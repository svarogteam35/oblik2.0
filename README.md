# Облік — закритий вебпортал

Окремий проєкт для приватного репозиторію. Перегляд залишків і запланованих надходжень із iPhone, Mac та інших пристроїв. Запис складських операцій із сайту не передбачений.

**Стан: вихідний код підготовлений. Збірка, запуск із PostgreSQL і перевірка на сервері ще не виконувалися. Це не опублікований сайт.**

## Завантаження на GitHub

1. Розпакуйте `OblikPortal-private-source.zip` в окрему папку.
2. На [GitHub створіть репозиторій](https://github.com/new), наприклад `oblik-portal`.
3. Обов’язково виберіть **Private**. Самі файли не можуть установити приватність репозиторію.
4. Завантажте вміст цієї папки через **Add file → Upload files**, включно з `.gitignore`, або через GitHub Desktop. Файл `OblikPortal.csproj` має бути в корені репозиторію. Не завантажуйте весь проєкт настільної програми.
5. Переконайтеся, що біля назви репозиторію написано **Private**. Доступ до коду надавайте лише потрібним співробітникам у налаштуваннях репозиторію.

У GitHub немає звичайного режиму приватного репозиторію «будь-хто з посиланням»: людина має бути запрошена та ввійти у свій GitHub. Користувачам складу доступ до репозиторію не потрібен: вони отримають адресу самого сайту.

GitHub Pages призначений для статичних сторінок і не запускає цей ASP.NET-сервер. Потрібен сервер із .NET 10 або підтримкою Docker. [Приватність репозиторію](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/managing-repository-settings/setting-repository-visibility), [можливості GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages).

## Доступ до сайту

- Публічний екран містить тільки форму входу. Дані доступні після пароля та шестизначного коду автентифікатора.
- Відкритої реєстрації немає. Суперадміністратор видає одноразове запрошення в настільній програмі: **Сервісна панель → Сайт і MFA → Користувачі сайту → Видати запрошення**.
- Запрошення діє 24 години та споживається під час початку налаштування. Користувач має 5 хвилин, щоб додати показаний ключ у застосунок-автентифікатор і підтвердити код. Якщо цей етап перервано, потрібне нове запрошення.
- Кожна нова авторизація вимагає пароль і новий код. Збереженого обходу MFA немає. Сеанс закінчується через 30 хвилин бездіяльності або максимум через 8 годин. Оновлення списку в межах чинного сеансу не вимагає нового коду.
- Пароль використовується з наявного облікового запису програми. Старий незахищений формат пароля сайт не приймає: спочатку потрібно оновити пароль у настільній програмі.
- Фірми та склади визначаються сервером за дозволами користувача. Зміна адреси запиту не надає доступу до іншого складу. Закриття доступу адміністратором відкликає сеанси.
- У журналі адміністратора: входи, невдалі спроби, виходи, перегляди, час, логін, IP, повідомлені браузером відомості про пристрій, фірма, склад і кількість показаних записів. IP та браузер не є надійним підтвердженням особи чи точного ПК.
- Паролі, коди MFA, ключі автентифікатора, запрошення і токени сеансів у журнал не записуються.

## Сервер і домен

Використайте окремий піддомен на кшталт `oblik.example.com`, де `example.com` потрібно замінити вашим доменом. Основний сайт компанії залишається на своїй адресі. Не змінюйте його DNS-записи; створіть лише запис піддомену після вибору сервера.

1. Підготуйте тестову копію бази актуальної настільної програми. `schema.sql` додає лише таблиці вебдоступу; це не повна схема складської програми.
2. Адміністратор бази застосовує `schema.sql` і видає окремій серверній ролі мінімальні права за `database-permissions.sql`. Вебсервер не повинен працювати під власником бази або суперкористувачем PostgreSQL.
3. Налаштуйте секрети через змінні середовища хостингу за `.env.example`. Сам файл `.env` ASP.NET автоматично не читає.
4. Надайте серверу захищене з’єднання з PostgreSQL, бажано через приватну мережу. Порт бази обмежте адресою сервера. У браузер рядок підключення не передається.
5. Налаштуйте HTTPS і зворотний проксі. `OBLIK_TRUSTED_PROXY` — тільки фактична IP-адреса довіреного проксі. Прямий доступ до порту застосунку з Інтернету закрийте. Проксі має перезаписувати передані клієнтом forwarded-заголовки та встановлювати власні.
6. Налаштуйте резервні копії бази та окремо секретного ключа MFA. Обмежте доступ до них; увімкніть шифрування дисків і резервних копій на хостингу.
7. На тестовому сервері виконайте перевірки з `TESTING.md`. Лише після цього підключайте робочу базу і користувачів.

Dockerfile — рецепт для майбутньої збірки на сервері. У межах підготовки архіву збірка не запускалася. Для підготовленого контейнера налаштуйте HTTPS-проксі на внутрішній порт 8080, запустіть від непривілейованого користувача, обмежте ресурси. Не передавайте секрети через аргументи збірки чи Dockerfile.

## Захист і його межі

Передача даних: HTTPS; база: TLS із перевіркою сертифіката та імені сервера (`VerifyFull`). Секрети TOTP: AES-256-GCM; токени сеансів і запрошення зберігаються як SHA-256-хеші. Є захист від повторного використання коду MFA, обмеження спроб входу, CSRF-захист, захищені cookie і серверна перевірка прав на кожний запит.

Не вимикайте перевірку сертифіката бази. Якщо її сертифікат від приватного центру, установіть довірений кореневий сертифікат на сервері. Це не потребує налаштувань ПК користувачів.

Ключ `OBLIK_MFA_KEY` — випадкові 32 байти у Base64, створені адміністратором на сервері. Не зберігайте його в GitHub, логах або листуванні. Втрата ключа потребує повторного налаштування MFA. Заміна ключа без міграції зашифрованих секретів заблокує їх читання.

Це серверний доступ до даних, тому не є наскрізним шифруванням: серверу потрібні розшифровані дані для перевірки й відображення. Немає обіцянки «абсолютного» захисту. Перед робочим запуском необхідні перевірка на тестовій базі, налаштування сервера та незалежна перевірка безпеки.

Для кількох екземплярів сервера потрібні спільні захищені ключі ASP.NET Data Protection та обмеження запитів на проксі. Поточне обмеження за IP працює окремо на кожному екземплярі. Ключі Data Protection зберігайте у захищеному постійному сховищі хостингу, не в репозиторії.

Заборона індексації (`noindex`) лише просить пошуковики не показувати сайт. Захист даних забезпечує авторизація, а не приховане посилання.

Джерела: [TOTP RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238), [CSRF у ASP.NET Core](https://learn.microsoft.com/aspnet/core/security/anti-request-forgery).
